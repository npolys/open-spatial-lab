# Open Spatial Lab

Open Spatial Lab is a local Web of Worlds and spatial-computing demo. From the player lobby and launcher, an avatar can move among three authored  destinations—Location A, Location B, and Denver Skyport—while preserving supported identity, equipment, pose, and portal state.

## What you get

- A launcher and player lobby
- Three authored destinations: Location A, Location B, and Denver Skyport
- Local world servers plus a simple one-command startup flow
- Avatar and equipment selection
- Browser-based verification and release checks

## Requirements

The tested setup is macOS 13+ and Ubuntu/WSL with:

- Git 2.33+
- Node.js 22.x and npm 10.x
- Bash, `curl`, and `lsof`
- A current Chrome, Chromium, Brave, or Edge browser

Before cloning, confirm:

```bash
git --version
node --version
npm --version
command -v curl
command -v lsof
```

## Repository layout

- `src/` — frontend server and topology orchestration
- `runtime/` — world-server and scene runtime
- `web/` — browser app, authored worlds, and runtime assets
- `tools/` — launcher helpers and verification scripts
- `wow-spec/` — WoW schema and validation code

## Quick start

There is no build step or separate preflight step.

### macOS / Linux

```bash
git clone https://github.com/grigb/open-spatial-lab.git
cd open-spatial-lab
npm ci
npm start
```

Then open http://127.0.0.1:8143/ in a supported browser.

### Ubuntu / WSL

```bash
sudo apt-get update
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y bash curl lsof psmisc sed chromium-browser
npm ci
export PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium-browser
npm run start:ubuntu
```

`npm run start:ubuntu` isn't WSL-exclusive — it's `npm start` plus two things worth having on any Debian/Ubuntu-family Linux, not just WSL: it force-kills anything already listening on OSL's 5 ports first (`fuser`, from `psmisc` — the fix for a real, repeatedly-hit problem where a second, independent checkout of this repo silently keeps answering on port `8143` after this checkout's own stop/start cycle, serving stale code with no obvious error), and it defaults `PUPPETEER_EXECUTABLE_PATH` to the Debian/Ubuntu package path for Chromium if not already set. The underlying launcher (`launchOpenSpatialLab.sh`) itself has no distro-specific dependencies (`node`/`npm`/`curl`/`lsof` only) — `start:ubuntu` is a strictly-more-robust wrapper around it, not a separate code path. Only Ubuntu/WSL is actually tested (see Requirements); the wrapper's own port-cleanup mechanism (`fuser`/`psmisc`) is standard on most Linux distros, but its chromium-path default is a Debian/Ubuntu package-naming guess — safe even when wrong, since `find-browser.mjs` verifies the path exists before trusting it and falls back to its own broader search (which covers both the `chromium` and `chromium-browser` binary names) otherwise.

If you want the browser checks too, run:

```bash
npm run demo-check
npm run render-adapter-check
```

## Five-minute demo

1. On the launcher, choose **Enter as Player** to enter the lobby. Select **Start exploring** if the orientation card appears.
2. Move with `W`, `A`, `S`, and `D`. Hold `Shift` to run, press `Space` to jump, drag to look around, scroll to zoom, and press `C` to switch camera view.
3. Choose **Switch avatar**, select an included avatar, one worn item, and one held item, then choose **Apply**. Continue moving to see the selection remain with the player.
4. Walk through a lit portal; crossing is automatic. Visit Location A and Location B and compare their scenes and local models.
5. Return to the lobby and walk through Portal C to enter Denver Skyport. Use its return portal to continue the journey.
6. Open **Views** to return to the launcher. Open the Location A and Location B observer views to show the two local world servers.

## Controls

- Walk: `W`, `A`, `S`, `D`
- Run: hold `Shift` while moving
- Jump: `Space`
- Look/orbit: drag the primary mouse button or use a one-finger drag
- Zoom: mouse wheel or trackpad scroll
- Camera: `C` or the camera button
- Portal: walk through a lit portal; no extra command is needed
- Launcher: arrow keys to move, `Home`/`End` for first/last, `Enter` or `Space` to open, and mouse selection
- Avatar selector: **Switch avatar**, choose an avatar plus one worn and one held item, then **Apply**; `Escape` or **Cancel** discards pending changes

```bash
npm stop
```

The command stops the frontend and every local world server, removes runtime PID files, and releases ports `8143` and `18151`–`18154`.

```bash
npm stop
npm start
```

## Troubleshooting

- **Unsupported Node or npm:** confirm `node --version` is 22.x and `npm --version` is 10.x.
- **Install fails:** confirm network access, remove `node_modules`, and run `npm ci` again.
- **A port is occupied:** run `npm stop`. If the message identifies an unrelated process, stop that application or choose another machine.
- **The app behaves like an old build even after pulling latest / making edits (missing features, old bugs back):** another checkout of this same repo, started independently, may still be holding port `8143` (or one of the backend ports) — `npm start` in one checkout does not stop a server started from a different one. `npm stop`/`npm start` now force-kill whatever is actually listening on OSL's configured ports before starting (not just PIDs this checkout itself launched), which should prevent this, but if you ever run the frontend/backends directly (`node src/serve.js` / `node src/orchestrator.js`) outside these scripts, that protection doesn't apply. If in doubt, confirm what's actually serving the port before debugging application code: on Windows with WSL, `Get-NetTCPConnection -LocalPort 8143 | Get-Process` — if the owning process is `wslrelay.exe`, the real server is inside WSL; find it with `wsl -e bash -c "ps aux | grep serve.js"` and confirm its directory with `wsl -e bash -c "readlink -f /proc/<pid>/cwd"`.
- **A page looks stale:** perform a hard refresh in the browser.
- **A service is not ready:** run `npm stop`, then `npm start` and use the newly printed URLs. The supported topology has exactly five listeners: frontend `8143` and world servers `18151`–`18154`.
- **Browser verification cannot find Chrome:** set `PUPPETEER_EXECUTABLE_PATH` to a compatible browser executable and rerun `npm run verify`.
- **`?renderer=x3dom` doesn't seem to change anything:** a URL has only one `?`; a second `?` later on (e.g. `?role=player&intro=bypass?renderer=x3dom`) is parsed as part of the *previous* param's value, not a new param — `renderer` silently falls back to the stored `osl-renderer-preference-v1` preference or three.js, with no error. Separate every param with `&`: `?role=player&intro=bypass&renderer=x3dom`. See "How to tell which engine is actually active" below — the two engines look almost identical by design, so eyeballing the canvas won't tell you which one is running.
- **`npm run release-check` reports a file-count or hash mismatch:** `RELEASE-MANIFEST.json` is out of sync with the actual file tree — run `npm run generate-release-manifest`, review the added/changed/removed list it prints, then rerun `npm run release-check`.

## Render-engine adapter (three.js + X3DOM)

The shipped demo still uses the default three.js path. The repo also includes an experimental X3DOM preview that can be selected with `?renderer=x3dom` or the on-screen renderer toggle. The staged parity plan below (Phases 1-7) is complete — the core gameplay loop (movement, portal traversal with a live preview, equipment, peer/multiplayer avatars, HUD toasts, renderer selection) works under both engines against the same real backend. What remains out of scope is deliberate and documented below, not oversight.

**Why the two engines look almost identical:** that's the intended result of this parity work, not a sign the wrong engine loaded. Both paths build the scene through the same engine-agnostic `RenderAdapter` calls (`createGeometry`/`createMaterial`/`createAmbientLight`/etc. — see `mountCanonicalWorldContent`, `wow-scene.mjs`), share the same camera math (`orbit-camera-controller.mjs` has zero engine references), and X3DOM itself renders through WebGL, so matching geometry/materials/lighting/camera produces near-identical pixels. **To confirm which engine is actually active** rather than trust the pixels: check `window.__x3domLiveMode` in the console (only defined on the X3DOM path), inspect `#scene-mount`'s child element (three.js mounts a `<canvas>`, X3DOM mounts an `<x3d>` host), or read the Truth panel's **actual renderer** field (`std-txr-renderer`, written from the live adapter itself in `panel-truth-chrome-controller.mjs`, not from the URL).

**Phase 1 — movement & camera (done):** first-person mode (`C` to toggle, or the on-screen button), jump (`Space`), third-person orbit-follow, and a camera-wall occlusion approximation are all real, driven by `web/x3dom-movement-camera-controller.mjs` against the same backend-connected `LiveAdapter` session the three.js path uses. Verified by `tools/x3dom-spikes/spike-run-x3dom-movement-camera.mjs`.

**Phase 2 — portal traversal (done):** portals now render as real, findable geometry (`web/x3dom-portal-traversal-glue.mjs`), and crossing one works end to end — exit-intent/arrival backend calls, UM manifest sign-and-verify, active-endpoint promotion, and presence handoff all already ran under X3DOM for free (that logic lives inside `LiveAdapter` itself, shared by both render paths); what this phase added was the rendering reaction: recomposing the scene for the newly active world and remapping the camera through the portal frames on crossing. The live render-through-the-aperture preview the three.js path has (`portal-spatial-preview.mjs`, a second `WebGLRenderTarget` + clipping planes) had no X3DOM equivalent at this phase — added in Phase 6 and later rebuilt on X3DOM's `RenderedTexture` node (see "Portal-preview architecture — RenderedTexture rewrite" below). Verified by `tools/x3dom-spikes/spike-run-x3dom-portal-traversal.mjs`.

**Phase 3 — equipment via named anchors (done):** the avatar spawns with fixed-offset attachment anchors (`head`/`leftHand`/`rightHand`, mirroring `avatar-equipment-layer.js`'s own non-bone fallback-rig approximation — X3DOM has no bone/skeleton API to attach to directly) and equips a default item per slot on load; on-screen buttons cycle each slot through the real equipment catalog (`equipment-view.js`, unchanged, already engine-agnostic). Verified by `tools/x3dom-spikes/spike-run-x3dom-equipment-anchors.mjs`.

**Phase 3.5a — hardened Inline asset loading (done):** loading several `<Inline>` glTF nodes around the same time was found to intermittently throw inside X3DOM's own internals; `X3DOMRenderAdapter.createInlineAsset()` now queues every load through a single shared, app-wide FIFO (`runtime/scene-core/public/render-adapter/x3dom-render-adapter.mjs`) instead of relying on callers to serialize their own calls by convention — a structural fix ahead of peer-avatar rendering, where loads will be triggered by other players' network events on timing nothing in this app controls. Verified by a dedicated concurrency stress spike, `tools/x3dom-spikes/spike-run-x3dom-inline-load-queue.mjs`, run clean multiple times in a row.

**Phase 4 — HUD wiring (done):** toast notifications and the airport HUD overlay's projection mechanism (`web/x3dom-hud-glue.mjs`) are wired in — a toast fires on portal crossing, using the same shared notification chrome markup as the three.js path. The overlay's real storefront/traveler tags need airport-terminal content the X3DOM path doesn't mount yet (`x3dom-portal-traversal-glue.mjs` only mounts the generic canonical room for every world); the projection/LOD mechanism itself is still exercised and verified with a synthetic entity. The full inspector/debug panel (`panel-truth-chrome-controller.mjs`) turned out to need a much larger app.js-specific dependency graph than the other two components — explicitly scoped out of this phase rather than half-built. Verified by `tools/x3dom-spikes/spike-run-x3dom-hud.mjs`.

**Phase 3.5b — peer/multiplayer avatar rendering (done):** other co-present players now spawn as real avatars with mirrored equipment (`web/x3dom-peer-avatars-glue.mjs`) — as with portals and equipment, the underlying presence/broadcast data needed no new code (`LiveAdapter` already runs this for both render paths); this phase adds the X3DOM-side rendering reaction, built on Phase 3.5a's hardened Inline-load queue since peer spawns arrive on network-driven timing outside this app's control. Peer presence today is same-origin `BroadcastChannel`-based (real for multiple tabs/windows of one browser profile; not yet real cross-network multiplayer — an existing, separately-documented limitation, not new to this phase). Verified by `tools/x3dom-spikes/spike-run-x3dom-peer-avatars.mjs`.

**Phase 5 — renderer-selection UI + persistence (done):** a real on-screen toggle (`#btn-renderer-preference` in `web/index.html`) lets a user switch engines without hand-editing the URL. Clicking it stores the choice under the `osl-renderer-preference-v1` localStorage key and navigates with an explicit `?renderer=` set; on later bare navigations (no `?renderer=` param), `index.html`'s inline bootstrap script and `web/demo-shell-bootstrap.mjs` both consult the stored preference before falling back to three.js, with an explicit query param always taking precedence over the stored value either direction. This is the first localStorage usage anywhere in `web/`. Verified by `tools/x3dom-spikes/spike-run-x3dom-renderer-selector.mjs`.

**Phase 6 — remaining adapter gaps + live portal preview (done, later rebuilt):** an audit of every `RenderAdapter.createGeometry`/`createMaterial` call site found no real caller needing `circle`/`torus`/`capsule`/`points`/`sprite` — nothing built speculatively. Two real, previously-deferred gaps were closed instead: (1) `createGeometry("plane")` now respects a material's `side: "double"` request — X3DOMRenderAdapter's `_wrapShape()` bridges it onto the geometry element as `solid="false"` (X3DOM's `Plane` node inherits a `solid` field from `X3DGeometryNode`, default `true`/backface-culled), fixing the canonical room's walls, which were invisible from outside — verified by `spike-run-x3dom-wall-solid.mjs`. (2) A live portal-aperture preview shipped for the first time, via a hidden second `<x3d>` host polling `runtime.getScreenshot()` at ~10fps into an `ImageTexture` (`X3DOMPortalRenderer`) — showing a procedural placeholder room, no proximity gating yet. **This mechanism no longer exists**: it was fully replaced by a `RenderedTexture`-based rewrite (see "Portal-preview architecture — RenderedTexture rewrite" below); `X3DOMPortalRenderer` and its screenshot-polling path were deleted once the replacement was verified stable. Verified at the time by `spike-run-x3dom-portal-preview.mjs`, since rewritten to verify the new mechanism instead.

**Phase 7 — final regression consolidation (done):** a combined-load spike (`spike-run-x3dom-phase7-combined-load.mjs`) runs several earlier phases' features at once, the way a real multi-user session actually would, rather than each in isolation — two co-present peers with default equipment already loaded and a live portal preview already capturing, then one peer crosses a real portal while the other keeps observing. This caught the one interaction no single earlier phase's spike exercised: whether an observing client correctly evicts a departed peer's avatar once that peer is no longer co-present in the same world (it does — confirmed via `x3dom-peer-avatars-glue.mjs`'s existing `co_present` filtering, which already handled this correctly with no code changes needed). All 11 X3DOM-parity spikes now pass together in one run. Separately decided: extending `verify-demo.mjs` (the three.js path's full-journey regression script) to also drive X3DOM was assessed and, as the original plan anticipated, confirmed still out of scope — that script is deeply `window.__assembly`/three.js-canvas-specific (377 lines), and X3DOM remains an opt-in experimental path rather than the shipped default, so the dedicated per-feature `tools/x3dom-spikes/` suite remains the right-sized verification approach for it.

**Portal preview — real content (done, follow-on to Phase 6):** the portal-aperture preview no longer shows a fixed-color placeholder room — it now mirrors what `scene-runtime-controller.mjs` actually wires for the three.js path in production (`liveAdapter.resolvePortalDestinationContent()`, reused as-is), not a call-site reuse of the three.js compositing itself (`syncHostedSceneObjectMeshes` hardcodes `ThreeRenderAdapter` and reaches past it for raw material/geometry APIs X3DOM's plain-DOM mesh handles don't have; `mountAirportTerminalContent` is 100% raw THREE with no adapter indirection at all — both needed genuine X3DOM-native rebuilds, not ports). Delivered in four stages: (1) real destination color plus live hosted-scene-object sync for legacy worlds (`web/x3dom-portal-hosted-objects.mjs`'s `syncHostedSceneObjectMeshesX3dom`, kept fresh via this glue's own poll timer — `resolvePortalDestinationContent()`'s `subscribeHostedPoint` only fires when something actively re-polls, which three.js gets for free from an unrelated debug-panel poll loop that doesn't exist on the X3DOM path) and real authored-graph topology for the airport-bound portal (`buildWowScene`, confirmed genuinely engine-agnostic — minus `mountAirportTerminalContent`'s storefront/gate set-dressing and `mountWowSceneAssets`' real glTF loading, both deliberately deferred); (2) the destination camera now tracks the main camera's real pose every tick (`glueCameraThroughFrames`, reused as-is — real walk-past parallax, not a static shot) — deliberately not three.js's pixel-perfect on-screen crop (at the time, X3DOM exposed no live render-target texture to crop in a shader, only a `getScreenshot()` snapshot; a real render-target texture exists now, see "Portal-preview architecture — RenderedTexture rewrite" below, but pixel-perfect cropping still hasn't been attempted against it); (3) proximity/visibility gating skips capture and camera-gluing when the aperture isn't on-screen (`X3DOMRenderAdapter.worldToScreen()` + a new `canvasSize` accessor, clipped against actual canvas bounds — an early draft that skipped the canvas-clipping step incorrectly treated any in-front-of-camera aperture as "eligible" even when projected entirely off-screen to the side, caught by this stage's own verification spike). Verified by `spike-run-x3dom-portal-hosted-objects.mjs`, `spike-run-x3dom-portal-preview-real-content.mjs`, `spike-run-x3dom-portal-preview-camera-glue.mjs`, and `spike-run-x3dom-portal-preview-gating.mjs`.

**Manual-QA bugfix pass (done):** three real bugs, found via manual play-testing rather than a spike (the existing suite's assertions weren't checking the specific thing that was actually broken in each case) — none were regressions from a stale test environment, all reproduced against a freshly-built server:
1. **Orbit camera mouse-drag did nothing.** Root cause, confirmed by tracing raw DOM event propagation: X3DOM's own internal `<canvas>` calls `stopPropagation()` on every `mousemove` over it (for its own hover-picking), so `x3dom-movement-camera-controller.mjs`'s bubble-phase listener on `window` never received a single `mousemove` during a real drag — `mousedown`/`mouseup` were unaffected, only `mousemove` was silently swallowed. Fixed by registering all three listeners in the capture phase instead, which runs before the canvas's own bubble-phase handler gets a chance to stop it.
2. **Equipped items (hat/torch/hammer) rendered ~5x too large.** The `equip-*.glb` assets are authored at a scale `avatar-equipment-layer.js` (the three.js path) already silently corrects with a flat `0.2` scalar on the raw asset root — `X3domGltfHumanoidProvider.attachItem()` never applied the equivalent correction, so the catalog's own `localTransform.scale` (usually `1`) was the only scale ever set. Fixed by post-multiplying the same `0.2` factor after the catalog transform applies, mirroring the three.js structure without adding an extra Transform node (this Inline-pool wrapper is a permanent, reusable pool member per `disposeNode()`'s own contract — wrapping it in a second node would leak one on every re-equip). `spike-run-x3dom-equipment-anchors.mjs` only ever asserted translation and parenting, never scale, which is why this shipped unnoticed — now also asserts scale.
3. **Portal apertures rendered as a fully opaque black rectangle, not a preview window.** Isolated via a live side-by-side: cloning the exact same live `<imagetexture>` node (proven non-black by decoding its captured PNG) onto a fresh `<plane>` rendered it correctly, while the existing aperture geometry — a thin `<box>` — stayed solid black regardless of material/lighting changes; box geometry's default UV mapping simply never visibly textures in this X3DOM build. Box was chosen in Phase 2 specifically to dodge single-sided plane visibility, but Phase 6 already closed that gap (`side: "double"` bridges to `solid="false"` on planes) without this phase's author revisiting the aperture's own geometry choice. Fixed by switching the aperture to a double-sided plane, getting correct two-sided visibility and working texture rendering together. `spike-run-x3dom-wall-solid.mjs`'s double-sided-plane count assertion was updated accordingly (portal apertures are now double-sided planes too, not just the two canonical walls).

**Manual-QA bugfix pass, round 2 (done):** a further round of live play-testing (immediately after round 1 above shipped) found two more real bugs, plus one report that turned out to be the environment problem below, not a code bug:
1. **Orbit camera had visible roll — the horizon tilted while turning, instead of staying level.** Root cause: `setCameraPose()`'s orientation math (as fixed in round 1's box/plane investigation era) derived the camera's rotation as a single shortest-arc rotation from the default forward direction to the target forward direction. That's roll-free only when azimuth or polar is zero in isolation — direct derivation confirmed combining both (ordinary orbit navigation does this constantly) tilts the rotation axis off-horizontal, rolling the "up" vector out of the vertical plane. Fixed by rebuilding the orientation from a proper right/up/forward basis (Gram-Schmidt against world-up, the same construction three.js's `Matrix4.lookAt`/OpenGL's `gluLookAt` use), which keeps azimuth and polar roll-free by construction — verified live (`up · right == 0` exactly, for a combined-azimuth-and-polar pose that previously rolled). Not built on X3D `Viewpoint.centerOfRotation`: that field only feeds X3DOM's own built-in EXAMINE navigation, which this app doesn't use (see bug 1 in round 1 — X3DOM's canvas swallows mouse events regardless of navigation mode, so camera control is fully hand-rolled here).
2. **Idle equipment-catalog assets ("lots of crowns") were visible scattered in the scene, not just the one actually equipped.** Root cause: `x3dom-inline-pool.js` pre-seeds 32 `<Inline>` slots at parse time so each has the one real load X3DOM requires before its URL can be reliably swapped later (see that file's own header comment) — but every slot's placeholder asset is `equip-crown.glb`, and no slot was ever hidden by default. Unclaimed slots (~28 of 32 in a typical session) sat at the world origin rendering a full, un-scaled crown each, all the time. Fixed by defaulting every pool slot's wrapper to `render="false"` at seed time, with `createInlineAsset()` now setting `render="true"` on claim and `disposeNode()` setting it back to `"false"` on release.
3. **"No portals rendered" — not a real bug, the recurring stale-server environment issue (see Troubleshooting).** A live test against a freshly-confirmed-correct server showed both portals rendering exactly as round 1 left them; this report coincided with the same second-checkout-on-port-8143 problem documented below recurring mid-session. `stopOpenSpatialLab.sh` (and therefore `launchOpenSpatialLab.sh`, which calls it) now force-kills whatever is listening on OSL's configured ports before starting, not just this checkout's own tracked PIDs, specifically to stop this from recurring.

**Manual-QA bugfix pass, round 3 (done):** one more real bug (avatar not turning), a performance fix for two reported symptoms, and a confirmed test artifact:
1. **The avatar model never rotated to face its movement direction under WASD.** Real, straightforward gap: `LiveAdapter.stepAvatar()` already computes a backend-authoritative heading (`state.avatar.rotation_y`, the same field `avatar-equipment-layer.js` applies to `avatarRig.rotation.y` on the three.js path) — but `HumanoidProvider`, the newer engine-agnostic avatar interface X3DOM uses, only ever had `setPosition`, never a rotation equivalent, so nothing on the X3DOM path ever applied it. Fixed by adding `setRotation(handle, yawRadians)` to the `HumanoidProvider` interface and `X3domGltfHumanoidProvider` (wrapping the adapter's existing `setRotationAxis(node, "y", radians)`), then calling it every frame in `x3dom-live-mode.mjs` for the local avatar and `x3dom-peer-avatars-glue.mjs` for peers (`peer.rotation_y`). Verified live: rotation attribute now tracks the backend heading exactly (e.g. walking with `camera_yaw: -PI/2` produces `rotation="0 1 0 -1.5707963267948966"`).
2. **Orbit camera "not smooth" + portal aperture "flashing" — both traced to the same real, measured main-thread contention from portal-preview screenshot capture, not separate bugs.** Direct measurement (recording `onEnterFrame` call timing) found the app running at a genuinely choppy ~5fps average with stalls up to 1.6s — confirmed via a controlled comparison (capture active vs. the synchronous `getScreenshot()`/`toDataURL()` PNG-encode work stubbed out) that portal-preview capture was responsible for a large share of the worst-case stalls (933ms → 246ms with two portals capturing). Separately, sampling the rendered aperture's on-screen pixels over time found periodic drops to pure black correlated with each captured-texture swap — consistent with (though not fully proven; see caveat below) a brief blank/reload flash on every `<imagetexture>` url update. Per explicit user direction, `X3DOMPortalRenderer`'s capture interval was raised from the original 100ms (already a throttled compromise, see its own header comment) to **1000ms** — confirmed via re-measurement to cut mean frame time from 191ms to 79ms and worst-case stalls from 1609ms to 396ms. **Caveat, stated honestly rather than implied away:** the flash-frequency pixel-sampling did NOT scale down proportionally with the interval change (still ~4 flashes in 8.7s at 1000ms vs. ~6 in 7.7s at 250ms), which is inconsistent with "one flash per capture" — raises real suspicion that the sampling method itself (reading a WebGL canvas via `drawImage` from JS, which can race the GPU's own clear/render cycle) may be partly or wholly a measurement artifact rather than something a user's own eyes would see on screen. (This entire mechanism — the hidden hosts, the capture interval, the flash artifact and its intermediate canvas/`Image` round-trip — no longer exists as of the `RenderedTexture` rewrite below, which has no capture step to flash or throttle.)
3. **An earlier "portal preview resets to blank mid-session" finding was a test-script artifact, not a real bug.** The diagnostic script used to investigate it walked the avatar forward for a fixed duration with no stop condition and ended up driving it straight through the portal (confirmed: `location_id` changed mid-walk) — the observed "reset" was `handleCrossing()`'s correct, expected world-content rebuild reacting to a real crossing the test caused by accident. Re-tested properly (walk to just outside the trigger radius, then stop and hold): both portals' preview state stayed stable and continuously updating over a multi-second sample window, no resets.

**Manual-QA bugfix pass, round 4 (done):** two more real bugs — one X3DOM-specific, one genuinely shared/backend code affecting both render paths equally — plus one honestly-unresolved gap surfaced along the way:

## Portal-preview architecture — RenderedTexture rewrite (done)

The screenshot-polling pipeline above (hidden `<x3d>` host, `getScreenshot()` polling, capture throttling) has been fully replaced. X3DOM's `RenderedTexture` node (Texturing component) turns out to be a genuine GPU render-to-texture primitive — two earlier investigation rounds left it unproven (a real `GL_INVALID_OPERATION` feedback-loop error, then a properly-configured node that still produced no visible output for unisolated reasons). A third round found and fixed both root causes:

- **The right isolation mechanism was `excludeNodes`, then it wasn't.** Reading `renderRTPass()`/`getViewMatrix()` directly out of the vendored `x3dom-full.js` found that `RenderedTexture` has its own `scene` field: set it, and the node recomputes drawables from ONLY that referenced subtree — the consuming aperture is never part of what's rendered, no exclusion bookkeeping needed at all (and it sidesteps a second bug: leaving `scene` unset makes the viewpoint's view-matrix wrongly inherit the consumer's own ancestor transform).
- **The second-round "no visible output" mystery was a test-harness bug, not an X3DOM one.** Three follow-up attempts hosted inside the live app kept reading a flat, unchanging dark pixel despite the `scene` field being verifiably wired correctly — traced to the live app's own third-person camera-follow loop silently overwriting the test's manual camera placement every frame. Moving the test to an isolated page with no competing camera logic fixed it immediately, and Stage 0 passed clean on all required checks: no feedback-loop error, the aperture shows destination content, `update="always"` gives genuinely continuous updates, and — the harder case — a brand-new node created and appended to the destination subtree well *after* the RenderedTexture was already live is picked up correctly.

**What changed in production:** each portal's destination-world content now builds directly inside the SAME document as the main scene — a real child of the shared scene root, staged at a large per-portal offset (2000m+, `STAGING_OFFSET_BASE_M` in `x3dom-portal-traversal-glue.mjs`) far outside the player's normal view — with `X3DOMRenderAdapter.createRenderedTexture()` (X3DOM-only, same category as `createClipPlane`) attached as the aperture material's texture map, rendering that staged subtree continuously. Its own nested viewpoint is driven every frame by the same `glueCameraThroughFrames()` math the old architecture used, just offset into the staging area. `X3DOMPortalRenderer` and the whole hidden-host/screenshot/capture-throttle mechanism were deleted once this was verified stable — there is no fallback to the old pipeline.

**A real, non-obvious cost of sharing one document, found and fixed:** X3D's Viewpoint `zNear`/`zFar` default to `-1` ("automatic," recomputed every frame from the WHOLE scene's bounding volume) — staging content hundreds of meters away balloons that computation and wrecks depth precision for everything close to the player. A live measurement found `zNear`/`zFar` jumping from `~0.002/19` (room-only) to `~0.12/1200` the moment 1000m-distant content entered the scene. Fixed by giving the main viewpoint (`web/index.html`'s `#x3dom-viewpoint`) and each `RenderedTexture`'s own nested viewpoint explicit values instead — confirmed this fully bypasses the automatic computation and that staged content becomes genuinely invisible from the main camera once beyond the explicit far plane.

**A second real bug, found only once this ran against the full live app, not any isolated spike:** every isolated reproduction attempt — single- and multi-portal, `attach()`-mounted, transparent aperture materials, async population gaps, all combined — worked perfectly. The live app, running with its real avatar, equipment, and peer-avatar Inline-loading activity, did not: portal apertures rendered fully black, with a real, repeating `GL_INVALID_OPERATION: Feedback loop formed between Framebuffer and active Texture` in the console. Root cause: the `scene` field's DOM-based `<... containerField="scene" USE="...">` resolution — reliable in every isolated test — silently failed to bind at the live app's real scale/concurrency, leaving `RenderedTexture` on its "reuse the main scene" fallback path, which includes the consuming aperture itself. Fixed by binding `scene` via a direct JS node-reference assignment (`X3DOMRenderAdapter.bindRenderedTextureScene()`) instead of routing through DOM mutation timing at all — the same category of fix this project has used before for dynamically-created-node quirks (the Inline pool, the shared Inline-load queue). Each RenderedTexture now also starts at `update="none"` and only flips to `"always"` once binding actually succeeds, closing the narrow window where the feedback loop could occur at all.

**A genuine capability improvement, not just parity:** the old hidden-host architecture had no way to pause a mounted `<x3d>` host's own render loop, stated at the time as an unfixed limitation. `RenderedTexture`'s `update` field can be flipped to `"none"` directly — `x3dom-portal-traversal-glue.mjs`'s existing proximity/visibility gating (`isPreviewEligible()`) now genuinely pauses each portal's destination render pass when its aperture isn't on-screen, not just the polling/compositing step on top of it.

**Performance, measured honestly rather than assumed:** the architecture removes real, structural costs — no second WebGL context, no PNG encode/decode, no capture-interval throttle, no flash-to-black artifact (no intermediate canvas/`Image` step left to race). Under this project's actual test environment (headless Chromium + SwiftShader software rendering), the measured frame-rate win over the old architecture's own documented ~5.3fps baseline was modest, not dramatic (~5.8-6.4fps, with pausing both RenderedTextures entirely recovering only ~7% — confirming the RT render passes aren't the dominant cost in *this specific* software-rasterized environment). The architectural wins this removes (extra GPU contexts, PNG round-trips) are real regardless and should matter far more on real GPU hardware, where render-to-texture is cheap and software-rasterization/context-switching overhead doesn't dominate — that comparison hasn't been made in this project, which only runs headless.

**A residual root-caused and fixed in a follow-up pass:** location-a's boot was logging 4 `GL_INVALID_OPERATION` feedback-loop warnings during the brief window before `bindRenderedTextureScene()` completed (down from 50+ continuous before the `update="none"`-until-bound fix above) — location-b, with the same 2-portal topology, logged zero. Root cause: a second, independent writer of the same `update` field. `tick()`'s own proximity/visibility gating (`isPreviewEligible()`) runs every frame and can flip `update` to `"always"` based purely on on-screen eligibility — with no knowledge of whether `bindRenderedTextureScene()` had actually completed for that portal yet, since the preview record is visible to that loop from the moment it's created, well before the async bind resolves. On a frame where a portal was already eligible but not yet bound, `tick()` could flip `update` away from `"none"` independently of (and racing) `setupPortalPreview()`'s own bind-then-flip sequence — reopening the exact `scene`-defaults-to-main-scene feedback loop the `update="none"`-until-bound fix was meant to close. Confirmed via direct instrumentation of the RenderedTexture nodes' internal `_vf.update`/`_cf.scene.node` state: `update` was observed as `"always"` while `scene` was still unbound, at a real, non-deterministic timing window (reproduced in ~2 of 3 fresh-boot runs before the fix, 0 of 5+ after). Fixed by gating `tick()`'s toggle on a `record.sceneBound` flag, set only once the real bind succeeds — `tick()` can no longer flip to `"always"` ahead of the bind, regardless of frame timing.

**Two follow-on visual-quality fixes, and one dangerous combination avoided along the way.** The initially-shipped aperture rendered upside-down and with blocky, grainy filtering. Both have real, individually-documented causes: `RenderedTexture`'s framebuffer output comes out vertically flipped relative to normal X3D texture sampling, and `TextureProperties`' `magnificationFilter`/`minificationFilter` both default to `"FASTEST"` (nearest-neighbor, confirmed via `x3dom-full.js`'s own filter-mapping tables) rather than smooth filtering. X3D has a real `flipY` field for the first (inherited from the shared `X3DTextureNode` base class, not listed on `RenderedTexture`'s own doc page but confirmed present, and already used by X3DOM's own glTF loader for the same purpose) — but setting `flipY="true"` on the `RenderedTexture` element **together with** a `<TextureProperties>` child on that same element was confirmed live to break unrelated rendering elsewhere in the document: the player avatar's own diffuse-mapped body went fully invisible (equipment items using flat, untextured materials were unaffected — consistent with, though not conclusively isolated to, some shared WebGL texture-pipeline state getting corrupted by that specific combination). Each field individually was confirmed safe; only the combination broke it. Fixed by never combining them on the `RenderedTexture` element at all: `TextureProperties` (smooth filtering) stays there, and the vertical flip is applied instead via a `<TextureTransform scale="1 -1">` on the *consuming* aperture material — confirmed via a dedicated rigorous test (an asymmetric red-top/green-bottom destination scene, since every prior center-pixel-sample spike couldn't have detected a flip at all against a uniformly-colored test scene) that this produces correct top/bottom orientation with no reproduction of the avatar regression.

**Orbital camera drag smoothness, root-caused and fixed:** a user report that the third-person orbit camera "skips frames" while dragging turned out to be a real X3DOM render-loop gotcha, confirmed by reading `X3DCanvas.prototype.tick` directly in the vendored source: X3DOM's `requestAnimationFrame` loop runs unconditionally every frame, but everything inside it — including `onEnterFrame()` callback dispatch, which is what drives the camera controller's own per-frame `step()` — is gated behind `doc.needRender`, a flag X3DOM only sets itself in response to its own DOM-attribute/field-change tracking. The mouse-drag handler only ever mutated plain JS state (the orbit controller's target angles), never an X3D DOM attribute, so it had no way to guarantee `onEnterFrame()` kept firing while the user was actively dragging — input could pile up invisibly until something unrelated happened to wake the render loop again. Fixed with a new `X3DOMRenderAdapter.requestRender()` primitive (X3DOM-only — three.js's default loop is unconditional and has no equivalent need) that calls X3DOM's own public `x3dElem.render()` wake-up hook; wired into the drag handler (every `mousemove` while dragging) and into the camera's own per-frame `step()` (kept alive only while the damped ease-out toward the released target hasn't yet settled, so the loop still goes idle once movement actually stops). Verified with a dedicated spike (`spike-x3dom-orbit-drag-render.html`/`spike-run-x3dom-orbit-drag-render.mjs`) that directly confirms `requestRender()` sets `doc.needRender`, the exact flag the render loop gates on.

**Peer-avatar co-presence spike flake, root-caused and fixed:** `spike-run-x3dom-peer-avatars.mjs` intermittently failed with a one-directional "page 2 never sees page 1" pattern under the full sequential suite. Root cause, once diagnosed: `x3dom-peer-avatars-glue.mjs`'s own `sync()` (which processes incoming BroadcastChannel presence messages) only runs from `onEnterFrame()` — same gating as the orbit-camera bug above — and a backgrounded Puppeteer page genuinely receives zero real `requestAnimationFrame` callbacks in headless Chrome (a documented, already-known test-harness characteristic, not a bug in the app). The spike already used `page.bringToFront()` to work around this, but relied on a fixed sleep afterward, which wasn't reliable margin under the resource contention of a ~30-spike sequential run — and a *second*, independent issue compounded it: the peer-presence reducer prunes a pose as stale after 4 seconds with no fresh broadcast, and the backgrounded sender page's own heartbeat had gone quiet, so even a successfully-woken receiver could still miss a narrow freshness window. Fixed by replacing the fixed sleep with a coordinated poll that re-broadcasts from the sender (via a direct `stepAvatar()` call over CDP, which isn't rAF-gated and works regardless of foreground/background state) and forces a render on the receiver every tick, removing the dependency on real elapsed-time-based rAF delivery entirely. Verified clean across 5 consecutive fresh-boot runs (was intermittent, roughly 1 in 3 failing, before the fix).

**Regression-suite performance — investigated, reverted:** the 34-spike sequential suite is slow largely because every spike independently launches its own full Chromium process (confirmed directly in `verify-render-adapters.mjs`: each spike runs as a separate `node` process via `spawnSync`, and every spike's own script calls `puppeteer.launch()`). A shared-browser consolidation (the orchestrator launches one Chromium process and each spike connects to it via `puppeteer.connect()` instead of launching its own, using an isolated `BrowserContext` per spike to preserve test isolation) was built and applied to all 34 spikes, but found non-viable in this environment: `puppeteer.connect()` navigation reliably hangs from a separate child process (confirmed in isolation, reproduced 3 times, unrelated to incognito contexts — even a plain `connect()` + `newPage()` on the default context hangs with zero network activity observed). Fully reverted to per-spike `puppeteer.launch()`, which is proven-reliable, at the cost of the suite's current wall-clock time. A genuine speedup would need the spikes to run in-process as importable functions rather than spawned child processes — a materially larger, riskier refactor than the connect()-based approach, not attempted here.

## Production hardening

The shipped demo is a trusted, single-machine, single-user local app: `src/serve.js` binds to `127.0.0.1` only, and each world server holds one global mutable avatar per process rather than per-user session state — a 2026-08 security review found that state model, not missing headers or CORS config, is the binding constraint for a public, multi-user deployment; those are still real gaps but secondary.

**Landed:** two stored-XSS fixes in the HUD's HTML rendering, peer-supplied avatar-equipment fields validated against the fixed catalog, a depth cap plus try/catch on spatial-graph node writes to remove an unauthenticated-crash path, a fix for a connection-leaking oversized-request handler, and a process-level crash guard around the four world servers.

**Planned:** OAuth at the gateway feeding per-user session state in `runtime-state.js` (replacing the single global `state.avatar` and the unauthenticated, free-text `player_id`), then perimeter hardening (CORS allowlisting, security headers, rate limiting, WebSocket auth) and `wow-spec` schema tightening once that identity-aware state model is in place. No delivery dates are set; see [Planned improvements](#planned-improvements) for the rest.
